# Збирання на ПК

Для ПК-прототипу обрано **C++17** і **CMake**. Потрібні компілятор із підтримкою C++17 та CMake. Навігаційне ядро має залишатися незалежним від ОС; файловий ввід, транспорт і тестовий запуск належатимуть до окремих адаптерів.

Для збирання й перевірки мінімального CLI на macOS або Linux з кореня репозиторію:

```sh
cmake -S . -B build
cmake --build build
./build/kpi4_cli --help
ctest --test-dir build --output-on-failure
```

Щоб перевірити побайтовий ввід із файлу або stdin:

```sh
./build/kpi4_cli --input fixtures/heartbeat_v2.bin --chunk-size 5
cat fixtures/heartbeat_v2.bin | ./build/kpi4_cli --input - --chunk-size 5
```

`--chunk-size` задає максимальний розмір порції від 1 до 65536 байтів. CLI повідомляє кількість байтів, порцій, повних MAVLink-кадрів із коректним CRC (`accepted`), відхилених кадрів (`rejected`) і поточних неповних кадрів на кінці потоку (`incomplete`, 0 або 1). Зі змісту повідомлень наразі декодується `HEARTBEAT`.
CLI має один вхідний потік, тому позначає його канал як `Unspecified`. Протокольний `FrameReader` приймає `InputChannel` для кожного байта (`Unspecified`, `GroundStation`, `ControllerX`) та зберігає окремий стан і лічильники для кожного каналу; подія містить канал походження. Це логічні мітки потоку, а не налаштування фізичного контролера чи транспорту.
Для кожного прийнятого кадру перед підсумком з'являється рядок `frame time=...Z mavlink=... sysid=... compid=... msgid=... seq=... len=... signed=...`. `time` — UTC-час прийому останнього байта на ПК з точністю до мілісекунди; `len` — довжина payload у байтах. `signed=yes` означає прапорець підпису в заголовку MAVLink 2, а не перевірену автентичність.
Для `HEARTBEAT` додається рядок `heartbeat channel=... sysid=... compid=... type=... autopilot=... status=...`. Назва і числове значення кожного enum виводяться разом; невідоме значення позначається `UNKNOWN`, зарезервоване — `RESERVED`. `channel` показує джерело байтів, а поля `type` і `autopilot` — заяву відправника в payload; вони не підтверджують, що повідомлення надіслав контролер.
Бібліотека `kpi4_protocol` також декодує `MISSION_COUNT`, `MISSION_REQUEST_INT`, `MISSION_ITEM_INT` і `MISSION_ACK` у типізовані події через `decode_mission_transfer`. Подія зберігає канал, відправника, адресата, тип місії та всі поля повідомлення без перетворення координат або параметрів. Передавати їй слід лише кадри, прийняті `FrameReader`; перевірка послідовності й повноти upload належить наступним крокам. CLI поки показує загальні метадані цих кадрів, без інспектора місії.
Перевірка CRC не є перевіркою автентичності відправника; політика ключів для підписаних MAVLink 2 кадрів ще не налаштована.
Лічильники `bad_crc`, `bad_signature` і `invalid_header` деталізують причини відхилення. Потік із шумом та пошкодженими кадрами можна перевірити командою `./build/kpi4_cli --input fixtures/recovery_stream.bin`.
Поточне відновлення повторно використовує стартовий байт, який завершив відхилений кадр. Це перевірено для кадру без останнього байта CRC; втрата байтів раніше в кадрі може приховати наступний кадр до чергової синхронізації.
Кількість фактичних порцій може відрізнятися між файлом і stdin через буферизацію.

На поточній машині збірку перевірено з Apple Clang 17.0.0 і CMake 4.4.4. `kpi4_core` поки є CMake-ціллю без реалізації. Фреймінг використовує локально включені [заголовки MAVLink](../third_party/mavlink/README.md).

Цей вибір визначає інструменти ПК-розробки. Компілятор для Raspberry Pi чи мікроконтролера, конкретна плата та профіль польотного контролера поки не вибрані й потребуватимуть окремої перевірки.
