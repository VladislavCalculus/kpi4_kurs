# Маршрут, шум GPS і відмова стану

```sh
./build/kpi4_demo --scenario route --noise 0.35 --fault stale --output build/route
```

Стенд використовує той самий [закон корекції та модель руху](guidance-demo.md). Внутрішній маршрут у метрах E/N від 50° N, 30° E: **(0,0) → (60,0) → (60,50) → (110,50)**. Початкова швидкість нульова, бажана — 8 м/с, знос — 2 м/с на північ; крок 0,05 с, час відгуку виконавця 0,5 с. Це демонстраційні параметри.

## Прогрес маршруту

`mission::RouteFollower` зберігає копію точок і мінімальний стан прогресу. Перша точка задає початок, друга — першу ціль. Увесь маршрут перевіряється через геометрію сегментів до видачі першої команди; порожній/вироджений або непідтриманий маршрут не запускається.

Викликач передає до `update()` тільки зразки, прийняті `StateValidator`. Радіус досягнення — 3 м за виміряним положенням. Проміжна досягнута точка перемикає сегмент, і той самий зразок одразу формує ціль для наступного відрізка з його бажаною швидкістю. Якщо кілька близьких цілей одночасно в радіусі, вони послідовно зараховуються. Перетин площини кінця без входження в радіус не пропускає waypoint: ядро повертає до нього.

Після останньої точки повертається `mission_completed` без команди та активного сегмента. Цей стан остаточний для створеного `RouteFollower`; новий маршрут потребує нового екземпляра. Завершення запису не моделює фізичне утримання, повернення чи посадку.

## Параметри сценарію

| Опція | Значення за замовчуванням | Допустимий діапазон / зміст |
| --- | --- | --- |
| `--speed` | 8 м/с | 4–12 м/с, бажана швидкість всіх цілей стенда |
| `--offset` | 0 м | ±20 м, початкове зміщення на північ |
| `--wind` | 2 м/с | ±5 м/с, сталий північний знос |
| `--noise` | 0 м | 0–0,5 м, амплітуда незалежного рівномірного шуму E/N |
| `--seed` | 42 | uint32, послідовність `mt19937` з явним перетворенням у double |
| `--fault` | `none` | `stale`, `missing` або `no_fix` на інтервалі [4,6) с |

Крім `--wind`, ці опції призначені для `--scenario route`; у сценарії одного відрізка вони відхиляються. Межі опцій не означають гарантованого успіху за всіх комбінацій. У ядрі швидкість задається окремо для кожної кінцевої точки; у CLI стенда однакова для всіх.

За `stale` повторюється зразок із часу 3,5 с з новим часом прийому. Поріг віку вимірювання — 0,1 с, тому весь інтервал дає `measurement_stale`. За `missing` провайдер не публікує зразка; за `no_fix` поточний зразок має відсутню GPS-фіксацію. Цикл зберігає видиму причину, не викликає `RouteFollower::update()` і не створює нової команди. Після відновлення придатних даних він продовжує той самий сегмент.

Умовна реакція виконавця на відсутність команди — нульова ціль швидкості з колишнім часом відгуку; боковий знос залишається. Цей вибір є політикою стенда, а не визначеним failsafe фізичного контролера.

## Результати та перевірка

`route.csv` містить істинний рух, виміряне положення й вік, активний сегмент, кількість досягнутих цілей, істинне поперечне відхилення, видану команду, ціль умовного виконавця, статус і причину стану. Для відсутнього зразка вимірювальні поля порожні; для відсутньої команди порожні `command_*`, а `model_target_*` дорівнюють нулю. Істинні величини використовуються лише для оцінки, не для корекції. `waypoints.csv` зберігає план, `summary.csv` — підсумкові метрики. Використовуйте окремі каталоги для різних сценаріїв.

До прогонів задано критерії `PASS`: усі три цілі за ≤60 с, істинна відстань при кожному переході ≤4 м, максимальне відхилення ≤`max(8 м, |offset|+2 м)`. Додатковий метр до виміряного радіуса враховує шум. За відмови очікуються рівно 40 відсутніх/відхилених зразків і відновлення команд після 6 с. Для успіху потрібні всі критерії; коди завершення: 0 — `PASS`, 1 — `FAIL`, 2 — помилка вводу/виконання.

[Збережені прогони D2](../devlogs/manual/D2-route-demo/README.md) охоплюють номінальний маршрут, шум ±0,35 м, початкові ±6 м при швидкостях 6/10 м/с і три типи відмови. `ctest --test-dir build --output-on-failure` також перевіряє неможливість просування маршруту без придатного стану, повернення до пропущеної точки, обмеження швидкості та повторюваність шуму за seed. Тести залишаються у Python й викликають виробничий C++ через bridge.
